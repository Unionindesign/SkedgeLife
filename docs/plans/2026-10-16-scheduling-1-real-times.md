# Scheduling 1: Real times

**Milestone:** "Scheduling 1: Real times" (#90–#95). **Parent plan:** [2026-10-03-scheduling-events-and-bookings.md](2026-10-03-scheduling-events-and-bookings.md). **Approved:** 2026-10-16 (go-ahead in chat, Mapbox confirmed for Phase 2).

## Goal

Replace free-text class times ("5:30pm Hot Ra") with events at real times and places that mean the same moment for everyone, following [`docs/rules/time.md`](../rules/time.md). Hosts create, edit, and cancel events from the app, and the Schedule tab shows upcoming dates in real local time.

## Scope

| Issue | What gets built |
|---|---|
| #90 Schema | `venues`, `events`, `event_occurrences`; `sync_event_occurrences()` expands weekly events into a 12-week window using the event's IANA zone (DST-safe), keeping cancelled dates; row-level security; `packages/data` queries; regenerated types. |
| #91 Migrate | A data migration turns `schedule_entries` into venues and `schedule_times` into weekly events (time parsed from the label, the rest becomes the title, `external_link` booking). Seed rewritten. Old tables dropped. |
| #92 Schedule tab | Upcoming occurrences grouped by day. In-person times in the event's zone, with the zone name when it differs from the device's; online in the device zone. Booking link-outs kept. Time-zone library chosen and recorded. |
| #93 Create / edit / cancel | One form: title, when (one time or weekly on chosen days), where (a saved place, a new place, or an online link). Optional: description, capacity, booking (RSVP placeholder or external link), interests, kind. "Private home" toggle with a confirmation. Cancel one date (and restore it) or the whole event. |
| #94 Caps | Free plan: 3 weekly slots and 1 larger group event a month, enforced by a trigger, mirrored in the app. |
| #95 Rolling window | A nightly `pg_cron` job tops every weekly event up to 12 weeks ahead. |

**Out of scope (later phases):** maps, geocoding, and venue search (Phase 2, Mapbox; needs a development build); bookings and RSVPs (Phase 3; "RSVP" is stored but does nothing yet); paid bookings (Phase 4); showing events on the public website (with #68); hybrid events in the form (the schema allows them); a start date for weekly events.

## Database

- **`venues`**: name, address, nullable `location geography(point)` (PostGIS, filled in Phase 2), IANA `time_zone`, logo, booking link, `created_by`, `is_private`. Shared between hosts: public read, creator-only writes. Private venues (homes) are readable only by their creator.
- **`events`**: host, title, description, interests, kind, format, venue, online link, `time_zone`, either one-off `starts_at`/`ends_at` or a weekly pattern (`weekly_days`, `local_start_time`, `duration_minutes`, optional `repeat_until`), capacity, booking mode and URL, visibility, status, `is_private_home`, and a public `area` shown in place of a private address.
- **`event_occurrences`**: `starts_at`/`ends_at` (UTC `timestamptz`) and status. Generated by `sync_event_occurrences()` from a trigger on `events`. Hosts may only change `status` (cancel or restore a date).
- **Regeneration on edit:** future scheduled dates no longer in the pattern are deleted; a cancelled date stays cancelled and moves to the new time on the same local day; past dates are never touched.
- **`upcoming_occurrences(profile_id)`**: upcoming dates using the server's `now()` (rule 8).
- **Caps trigger:** see Decisions.
- **Time zones** are validated as real IANA names (`UTC` or `Area/City`), never abbreviations or offsets.

## Screens

- **Schedule tab:** day headings ("Today", "Tomorrow", "Friday, Oct 17"), each date with time, title, place, and a "Book" link-out; cancelled dates struck through. "+" in the header adds an event. Tapping a date opens it for editing.
- **Event form (modal):** title → one time/weekly → date or days, start, end → in person/online → place or link. "More options" holds the rest. Editing a date offers "Cancel this date" / "Restore this date" and "Cancel event".
- **Date and time pickers:** `@react-native-community/datetimepicker` on the phone (runs in Expo Go), the browser's own inputs on the web build.

## Decisions

1. **What counts toward the caps.** Weekly events always use one of the 3 weekly slots, whatever their capacity. One-offs with capacity 20 or less use a slot in their week (Monday to Sunday in the event's zone). One-offs over 20 or with no limit are "larger" events: 1 per calendar month. Cancelled events don't count. Paid: no caps. The check runs only when an event's schedule, capacity, or status changes, so a downgraded account over the cap can still edit titles.
2. **Private homes, before bookings exist:** the exact address is visible only to the host; everyone else sees the area the host enters. Phase 3 lets people who booked see it.
3. **Online links are public for now**, since nobody can book yet. Phase 3 restricts them to people who booked.
4. **Weekly events store a duration**, not an end time, because a local end time can cross midnight. Occurrences still store `starts_at` and `ends_at` (rule 6).
5. **Time-zone library:** `@date-fns/tz`. It's small, built on `Intl`, and works in Hermes. It's used only for local-to-UTC conversion when saving a one-off; display uses `Intl.DateTimeFormat`.
6. **A new place's zone** defaults to the device's zone, with a short list to change it. Phase 2 fills it in from the map location.
7. **Migrated classes default to 60 minutes and `America/Los_Angeles`** (every current host is in Southern California).

## Built differently from the plan

- **Sequences moved to the left of the Schedule header** to make room for the **+** (add event) button on the right.
- **A free host hears about the weekly cap first:** the form puts that message before any field problems. Small one-offs that would overfill a week are refused by the database, and its message is shown.
- **Expo SDK patch updates** came along, as in #96, so `expo-doctor` passes.

- **Single dates are fully editable** (added in review, 2026-10-17). Tapping a weekly date opens "This date only" (with a switch to "Every date"): its time and day, title, description, place or link, capacity, and booking can all change for that date alone, and "Undo changes to this date" puts it back. A changed date stores only what differs from its event (`event_occurrences` detail columns, null meaning "same as the event"); `original_starts_at` records the slot it fills, so schedule edits leave it alone and don't refill its slot. A trigger marks host changes and checks the merged date still has a place or link; `reset_occurrence()` undoes them. Kind and interests stay per event.
